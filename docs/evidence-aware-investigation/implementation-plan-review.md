# Evidence-Aware Agent 实施计划评审意见

日期：2026-10-01  
评审对象：[Phase 2–5.1 实施计划](phase-2-implementation-plan.md)  
状态：待纳入计划修订；本文不代表已经完成修改或实现。

## 一、总体结论

计划的主体顺序合理：先建立数据、工具、预算、Trace 和评测，再实现基线与 Proposed，最后运行对照。独立实验包、离线 CI、延后真实 SOC 集成的范围也合理。

建议保留 M0–M8 主体结构，在开工前补齐以下四项，并在对应里程碑补充其余验收要求。

核心风险是：工程运行成功，但实验结果不足以证明 Evidence-Aware 策略有效。优先解决充分性判定、基线公平性和实验结论边界。

## 二、开工前必须明确的四项

### R1：拆分工程验收与真实模型实验

**对应计划：**M8、最终交付。

**问题：**FakeScriptedModel 的响应由脚本指定，只能验证流程和指标实现。用它跑出的四方法成绩，不能证明调查策略优劣。原计划把真实模型留待后续触发，却把最终交付称为“对照基准报告”，需要明确报告性质。

**修改要求：**

- M8a：离线工程验收，使用假模型，验证流程、预算、Trace 和计分。
- M8b：真实模型探索，在相同模型条件下运行五个案例，观察实际行为与失败。
- 后续扩充数据并开展盲测和消融，再评估策略收益。

**验收标准：**报告标明模型模式和结论边界；假模型报告不出现算法优越性结论；真实模型尚未运行时，M8b 标记为未完成。五个公开设计案例即使用真实模型运行，也不作为泛化能力证明。

### R2：将公共 Evidence Registry 提前到 M4

**对应计划：**M4 Dispatcher、M6 基线、M7 registry.py。

**问题：**M4 已需要校验工具参数中的实体来自哪里，M6 已需要统一证据引用，而注册器到 M7 才实现。若注册器专属于 Proposed，还会使基线在证据加工和引用方面处于不公平条件。

**修改要求：**

- 公共注册器放入 runtime/，四种方法共用。
- 公共部分负责来源登记、确定性字段提取、ID 分配、去重、原文引用和调用关联。
- Proposed 单独维护竞争假设、支持/反驳关系、证据缺口、充分性与行动价值。

**验收标准：**相同告警或工具响应经过公共注册器得到等价事实与引用能力；基线无需依赖 agents/ 即可运行；注册器不访问 oracle。

### R3：明确数据边界，修正“物理隔离”表述

**对应计划：**依赖分层、M1 全量移植契约、M3 隔离、M5 泄漏测试。

**问题：**目录位置和 import 守卫属于代码约束，不等于进程或文件访问隔离。原 Phase 1 示例契约把运行时、环境和 oracle 类型放在同一文件，直接全部移植也会削弱边界。

**修改要求：**

- 运行时契约、工具环境契约、oracle/评测契约分别存放。
- MVP 进程内方案称为“逻辑隔离”，明确其保证范围；子进程加固仍可延后。
- 检查实际模型请求、工具描述和工具响应，确保隐藏标注没有进入 Agent。
- 使用隐藏字段、专用标记和数据来源检查泄漏，不能仅按 malicious、benign 等合法业务词匹配。
- C4/C5 不仅共享环境文件，还要检查实际模型可见内容；动态 ID 等字段采用预先定义的规范化规则，不能掩盖真实内容差异。

**验收标准：**Agent 执行路径无需读取 oracle；测试能发现故意混入提示的隐藏标记；正常假设和 verdict 不被误报为标签泄漏；C4/C5 的模型可见输入及同查询响应等价。

### R4：为充分性门槛补充可执行判定表

**对应计划：**M1/M2 设计输入、M7 sufficiency.py。

**问题：**JSON Schema 验证结构，不能验证“替代解释已排除”等语义判断。如果模型输出 met 就直接接受，充分性机制仍主要是自评分。

**修改要求：**每个门槛必须定义以下内容：

| 项目 | 内容 |
|---|---|
| 所需观察 | 哪些事实或记录能够参与判定 |
| 程序检查 | 来源、实体、时间、hash、参数、覆盖范围等可核查条件 |
| 模型解释 | 对证据与假设关系的解释，以及解释的适用范围 |
| 冲突处理 | 证据相互矛盾时如何阻断确定结论 |
| 无法验证 | 返回 unknown，不因结构正确就接受 met |

例如，“符合批准任务”至少核对实际执行与批准记录的 host、账号、时间、任务、hash 和参数。单独存在维护窗口不能通过此门槛。

**验收标准：**格式正确但引用不支持判断的 met 被拒绝；缺失字段和覆盖不足得到 unknown；规则按告警族定义，不按 case ID 判断；离线评分不直接调用运行时自评。

## 三、在对应里程碑补充的要求

### R5：补公共动作 Schema，保持 ReAct 基线独立

**对应计划：**M1 输出 Schema、M6 ReAct。

- 定义公共动作联合类型：ToolAction（工具名、参数）或 FinishAction（最终结果）。
- 不让 ReAct 被迫填写 Proposed 的假设关联、证据缺口和判别价值字段。
- Proposed 的调查计划通过适配转换成公共工具请求，额外状态保留在其内部。

**验收标准：**ReAct 能独立调用工具或结束；共享接口未隐式加入待验证的 Proposed 机制。

### R6：补齐报告与原始记录的对应关系

**对应计划：**M8 报告与 Trace 交付。

- 报告附运行配置、模型/数据/代码版本、逐案例结果、Trace 文件清单与哈希。
- 保存脱敏后的代表性成功和失败 Trace，注明完整记录的归档位置。
- 区分“重放已有记录并重算指标”和“重新调用模型运行实验”。

**验收标准：**能从报告定位到对应运行，使用保存的记录重新计算核心指标；重新调用模型得到不同结果时，不覆盖旧运行。

### R7：使用独立 CI job，并固定实验环境

**对应计划：**M0。

- 现有 CI 默认目录是 code/python；为 investigation 新建 job，明确工作目录和安装路径。
- 独立安装实验依赖并保存锁定版本；本地优先使用实验包自己的虚拟环境。
- 原产品“27 项通过”属于历史状态，作为待重新验证的基线。

**验收标准：**新包在干净环境可安装和测试；其测试不依赖原产品依赖偶然存在；两套测试结果分别显示。

## 四、可以简化或延后的内容

| 项目 | 建议 | 原因 |
|---|---|---|
| 五案例 bootstrap、零事件置信上界 | 当前只报告原始计数与逐案例结果，统计推断留待扩充数据 | 五案例用于功能验收；C4/C5 还是相关案例 |
| 25–30 个文件、60+ 项测试 | 删除数量承诺，改用风险验收清单 | 文件和测试数量不能代表质量 |
| 完整风险—覆盖曲线和复杂校准展示 | 先固定指标定义、保存所需数据，样本充足后分析 | 小样本曲线容易产生过度解读 |
| 子进程隔离 | 可延后，但当前只声明逻辑隔离 | 与 MVP 的实际保证保持一致 |

建议保留的关键验收：未获证据不能引用；空结果与数据缺失不同；所有模型调用计费；同源重复不增加独立证据；C4/C5 不泄漏真值；四种方法使用同一评分口径。

## 五、修订后的执行顺序

| 阶段 | 主要交付 |
|---|---|
| M0 | 独立包、依赖锁定、独立 CI job |
| M1 | 按访问边界拆分契约，增加公共动作 Schema |
| M2 | 五个 fixtures、独立 oracle、充分性判定表、输入边界验收 |
| M3 | Mock 工具、参数过滤、覆盖和错误语义 |
| M4 | 公共 Evidence Registry、预算、Dispatcher、Trace、模型接口 |
| M5 | 手算指标、独立评分、离线重放 |
| M6 | Direct、Fixed、ReAct 与 Fixed-All |
| M7 | Proposed 假设、充分性、调查策略和停止机制 |
| M8a | 假模型工程验收报告 |
| M8b | 真实模型五案例探索性报告，保存失败记录 |
| 后续 | 扩充盲测、消融，再决定是否接入真实工具 |

## 六、计划修订检查表

- [ ] R1：工程验收与真实实验分开命名、分开验收。
- [ ] R2：Registry 提前且由四种方法共用。
- [ ] R3：契约分区、逻辑隔离与实际模型输入检查写清楚。
- [ ] R4：充分性判定表有可执行条件与 unknown 处理。
- [ ] R5：ReAct 使用公共动作接口，不继承 Proposed 内部结构。
- [ ] R6：报告可定位原始记录并重算指标。
- [ ] R7：CI 和依赖环境独立，历史测试结果重新验证。
- [ ] 删除文件数、测试数作为交付标准的表述。
- [ ] 小样本统计与后续有效性实验的边界明确。

建议：完成上述计划修订后，再从 M0 逐层实施。优先级最高的是 R4 的判定机制和 R1 的实验结论边界。
