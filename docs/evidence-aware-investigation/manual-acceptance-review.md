# 人工验收流程评审意见

日期：2026-10-01  
评审对象：[实施计划 v3 的人工验收安排](phase-2-implementation-plan.md)  
状态：待纳入计划修订；本文件不代表相关修改或验收已经完成。

## 一、总体结论

保留“每个里程碑完成后暂停，由用户明确验收通过再进入下一阶段”的安排。

人工验收应帮助用户理解当前完成的能力、操作结果和局限。开发方先完成技术自检，并提供可复现的演示与证据；用户据此决定是否通过。

实施前优先解决提交与远端 CI 的顺序冲突，修正个别验收条件，并明确真实模型效果不佳不等于工程验收失败。

## 二、需要修改的条款

### A1：解决“验收后才提交”与“验收前查看 GitHub Actions”的冲突

**对应位置：**M0、里程碑提交规则、第 7 节。

**问题：**新的 CI 配置必须先进入远端提交才能运行。当前同时要求验收前查看新 CI 结果、验收后才提交，执行顺序冲突。M0 的“设计稿先行提交”也需要统一口径。

**推荐流程，尽量保留当前偏好：**

1. 完成代码、文档、本地测试及 CI 配置检查。
2. 用户进行本地人工验收。
3. 用户明确通过后提交；远端推送须在明确授权的范围内执行。
4. 运行远端 CI 并核对所测 commit。
5. 远端 CI 通过后进入下一里程碑；失败则修复并重新验证。影响已验收行为的修改需要再次人工验收。

此流程下，M0 的 GitHub Actions 检查应移到提交后的确认步骤。尚未推送或 CI 未运行时标记“待远端验证”，不能写成全阶段完成。

**备选：**允许先在验收分支提交并运行 CI，用户验收后再合并或标记里程碑完成。该方案改变了“验收前不提交”的约定，需要由用户选择，不能默认采用。

### A2：明确技术自检与人工验收的分工

**对应位置：**M1、M3、M5，以及提验要求。

**问题：**逐字节比较响应、审查 JSON Schema、走查 evaluator 代码等，不宜全部变成用户必须独立完成的技术任务。

| 开发方提验前完成 | 用户验收重点 |
|---|---|
| 自动测试、源码与依赖检查 | 操作是否能完成，结果是否符合说明 |
| 构造正常与异常输入，提供演示入口 | 异常是否被拒绝，原因是否易懂 |
| 生成差异报告、来源关联和完整记录 | 抽查结果是否有据可查 |
| 明确已知问题和限制 | 当前能力是否达到该里程碑范围 |

**建议表述：**“每个里程碑必须由用户明确验收。开发方负责先完成全部必要技术自检，并提供命令、预期结果和可核对证据；用户可以操作、观察演示或抽查记录后作出判断。源码阅读可作为学习与深入核查选项。”

例如 M5：用户修改一组小样本，手算 False Close Rate 并与程序比对；开发方另行提供评分模块独立性的代码检查与测试结果。

### A3：C4/C5 比较应处理允许变化的运行元数据

**对应位置：**M3 人工验收。

**问题：**完整响应中的 call_id、实际耗时等可能正常不同，原始字节完全相同并非正确目标。

**建议替换为：**

> 对 C4/C5 执行同一组合法查询。按预先冻结的规范化规则处理允许变化的运行元数据后，核对模型可见的业务内容、覆盖状态和成本语义一致，并审阅差异报告。

报告必须列明被忽略或规范化的字段及原因。不能在看到差异后临时扩大忽略范围。模型可见的元数据也不能编码案例真值；相同人工抽查查询不能替代自动化边界测试。

### A4：零工具预算的拒判测试需要限定初始证据不足

**对应位置：**M4 人工验收。

**问题：**max_tool_calls=0 表示不能再调用调查工具，并不自动说明当前证据不足。

**建议替换为：**

> 对初始证据不足且必须查询工具才能判定的案例，设置 max_tool_calls=0，确认不执行工具，并在没有已验证充分结论时输出确定性 Abstain，不进行额外免费模型总结。

如果告警已经包含充分证据，且其他预算允许完成判断，不应仅因工具预算为零而禁止有依据的结论。

### A5：失败 Trace 抽查应为条件项

**对应位置：**M8b 人工验收。

**问题：**真实实验不一定出现失败，不能要求必须存在一个失败案例才能验收。

**建议替换为：**

> 有失败运行时，至少抽查一个失败 Trace；没有失败时记录失败数为零，并抽查其他运行。通过单独的故障注入测试验证失败记录保存机制，不将故障注入结果混入真实实验统计。

### A6：分开判断工程是否正确与策略是否有效

**对应位置：**M7、M8a、M8b 的通过与退回标准。

| 情况 | 处理方式 |
|---|---|
| 漏记调用、预算失效、标签泄漏、评分错误 | 工程验收不通过，修复后重新验证 |
| 假模型流程不符合预设行为 | 检查实现或测试脚本，修复并保留问题记录 |
| 真实 Proposed 更贵、拒判更多或没有减少错误关闭 | 如实验执行正确，允许工程验收通过；记录研究假设未获支持或证据不足 |
| 真实输出偏离预期 | 先区分实现缺陷与模型/策略表现，再决定修复还是保留为实验发现 |

**建议表述：**“M7 的固定预期用于假模型和确定性逻辑验收；M8b 验收实验条件、执行正确性、记录完整性与结论诚实性，不要求真实模型必须达到预设效果。”

不得为了通过验收删除困难样本、修改真实标签，或只保留有利运行。调整策略后应创建新版本、新运行，保留旧结果。

### A7：验收结论绑定具体版本

**对应位置：**第 7.2 节记录表。

**问题：**只有通过/不通过、日期和备注，无法确定通过的是哪一份文件或实验结果。

**补充要求：**

- 提验版本：提交前使用文件清单与内容哈希等快照标识。
- 验收说明、测试报告和问题记录的路径。
- 验收人、日期、结论及未完成项。
- 通过后补记 commit ID；远端 CI 结果必须关联实际测试的 commit。
- 修复后列出变更和受影响验收项；开发方完成必要回归，用户重点复核受影响项。

## 三、建议的每里程碑流程

1. **实施与自检**：完成范围内工作、自动测试和技术审查。
2. **准备提验材料**：生成版本快照、简短说明、操作入口、预期结果和已知限制。
3. **用户人工验收**：用户操作或观察演示、抽查证据，明确通过或不通过；不能将未回复当作通过。
4. **问题修复与复验**：保留问题记录，说明修复影响，重新提验。
5. **提交与 CI 确认**：按 A1 选定流程执行；不将未完成的远端验证写成通过。
6. **进入下一阶段**：用户已明确通过，且本阶段要求的验证已完成。

每个里程碑仍单独验收，不跳过或合并；调整的是验收材料与操作负担，不是取消用户的决定权。

```text
里程碑：

这一步解决什么问题：
本次完成的能力：

操作步骤：
1. 操作或命令：
   应看到的结果：
   如何核对：
2. 操作或命令：
   应看到的结果：
   如何核对：

自动测试与技术自检结果：
报告 / Trace / 差异记录路径：
已知限制及未完成项：
需要用户判断的事项：

复验时补充：修改了什么、影响哪些验收项、回归结果。
```

## 五、验收记录模板

| 字段 | 记录内容 |
|---|---|
| 里程碑 | M0 / M1 / … |
| 提验版本 | 文件快照或 commit ID |
| 验收说明 | 文件路径 |
| 测试与演示证据 | 报告、Trace、差异记录路径 |
| 验收人及日期 | 用户与日期 |
| 人工结论 | 待验收 / 通过 / 不通过 |
| 问题及修复 | 问题编号、处理状态、复验范围 |
| 通过后 commit | 对应提交 |
| 远端 CI | 未运行 / 通过 / 失败；关联 commit 与运行链接 |
| 阶段状态 | 未完成 / 待复验 / 待远端验证 / 已完成 |
| 实验结论（如适用） | 支持 / 不支持 / 证据不足；与工程验收结论分开 |
